# 1.4.2：历史重写与旧克隆迁移

## 变更范围

1.4.2将摘要规则修订正式编号，并同步技能元数据、README、更新记录和发布说明。同时对主仓库可维护分支及历史版本标签做定点脱敏，保留正常版本记录、提交作者归属与通用规范示例，不整段删除历史。

本次清理的是已知私人项目痕迹和身份关系信息；公开文档只保留通用规则及验证结论，原始私人材料、逐项来源和本地备份不随仓库分发。受影响的提交编号会改变，旧标签会指向对应的干净历史；版本名称本身保留。

## 旧克隆不能直接合并更新

历史重写前的本地克隆或分支可能把旧内容重新推回。不要在旧克隆中直接执行`git pull`合并，也不要从旧分支向重写后的主仓库推送。

推荐做法：

1. 保留旧目录，检查是否有自己尚未提交或未发布的工作，不先删除或强制覆盖。
2. 在另一个新目录重新克隆：

```bash
git clone https://github.com/VictorTran1023/law-paper-writing-skill.git law-paper-writing-skill-1.4.2
git -C law-paper-writing-skill-1.4.2 switch --detach v1.4.2
```

3. 需要继续开发时，在新克隆中从干净的main新开分支；如有自己的修改，只迁移经人工核对的文件级变更，不合并旧分支的提交历史。
4. 已安装到Hermes、Codex或其他位置的副本也应按原安装方式迁移；重新指定正确的技能路径并确认读取到1.4.2。仓库更新或Release发布不会自动替换安装副本。
5. 旧目录和备份只作本地保留，未经审查不重新推送；是否删除由持有人决定。

已经从本次清理后的主仓库获取的克隆，后续可按README中的普通更新流程执行。

## 清理边界

主仓库分支、历史标签及GitHub Release的版本引用可以由维护者更新，但这不等于所有旧数据都已在互联网消失：

- GitHub的只读PR引用、缓存或按旧提交编号访问的视图，可能需要GitHub Support另行处理。
- 第三方派生仓库及其他人的本地克隆需要持有人配合清理，不能由本仓库更新替代。
- 身份信息与项目上下文属于已知模式核验，不能宣称检测覆盖任意未知格式的秘密。

处理方法和限制依据 [GitHub官方历史敏感信息清理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)。发现残留时，不应把原始私人内容复制到公开Issue、Release说明或讨论中。
